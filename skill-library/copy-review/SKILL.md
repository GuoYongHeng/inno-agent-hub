# 文案审稿（copy-review）

## Overview

面向大学生、实习生及职场新手的文案审校 skill。核心方法论基于八个常见通病维度，审稿产出两项交付物：**审稿报告**（总评 + 分级问题清单 + 事实核查结果 + 亮点保留）与**全文修订稿**（附改动对照说明）。

三条铁律：

1. **先见森林，再见树木**。任何逐句挑错之前，先通读全文判断整体——文种对不对、主题有没有、主线清不清。局部问题改得再好，整体立不住也是白改（对应通病八）。
2. **每条问题必须给证据和改法**。问题要引用原文、定位出处；建议要给出病因分析、修改方向和改写示范，杜绝"语言不够优美"这类空泛意见。
3. **不代做判断，只暴露风险**。涉及事实真实性，先列待核查清单交由调用者决定是否核查，不擅自跳过，也不擅自定罪。
4. **单位要求高于一切**。用户单位配置的硬性要求（`config/org-rules.md`）是**最高准则**：凡与通用规则冲突之处，一律以单位要求为准，并在报告中注明"该条按单位要求判定"。
5. **稳先于顺**。涉及成绩评价、问题定性、责任表述、改革创新、安全稳定、群众感受的内容，先过口径与分寸关（Step 3.5），再谈文采；口径风险**只列不判**，是否修改由人对照政策、上级口径与单位实际定夺。

## 触发条件

- 用户要求审校、批改、指出问题、提修改建议、润色、改稿，且文稿属于职场/校园正式或半正式文案
- 文种范围（详见 references/01-scene-matrix.md）：通知、总结、汇报材料、工作方案、宣传稿/新闻稿、简报、讲话稿、会议纪要、主持词、微信推文（含活动预告、比赛结果公示）、小红书文案
- 不适用：纯数据表格核对、代码评审、无文本内容的图片

## 审稿工作流

### Step 1：定场合

- 识别文稿文种与使用场景（正式会议宣读 / 平台发布 / 内部传阅 / 对外宣传等）
- 加载 `references/01-scene-matrix.md`，对照该文种的**结构骨架、语言风格、内涵底线**要求
- 若文种属于新闻稿（消息稿）、活动预告、比赛结果公示、主持词四类，**必须同时加载 `references/08-specialty-writing-guides.md` 对应章节**（含倒金字塔结构、导语提名规则、领导排序、意义取舍、预告要素清单、公示四步、主持词注音与报幕等专项检查点）
- **检查 `config/org-rules.md`：若已填写实际内容，加载并作为最高准则**——后续所有步骤的判定，凡与通用规则冲突之处，一律以单位要求为准；每条单位要求都要在诊断中逐条核对
- 明确本场合"必须有/绝不能有"的元素，作为后续诊断的标尺
- 输出：一句话场合判定，例如"本文为对上的年度工作总结，宜结构完整、数据支撑、措辞谦抑，不宜口语化"

### Step 2：通读抓整体

- 不逐句挑错，通读全文一到两遍
- 抓三件事：**主题是否唯一**（是否漂移/夹杂）、**结构是否完整**（开头—主体—结尾是否齐全）、**主线是否清晰**（各部分是否都服务同一目标）
- 记录整体印象，供 Step 7 总评使用

### Step 3：八维诊断

- 加载 `references/02-defect-diagnostics.md`，按八大通病逐维排查：
  1. 模糊场合、不分场景
  2. 只顾行文、不讲逻辑
  3. 不做调研、一想当然
  4. 用词粗放、表述不准
  5. 照搬机器、一眼戳穿
  6. 排版混乱、可读性差
  7. 空话泛滥、语言赘余
  8. 只见树木、不见森林
- 每条问题**必须引用原文**并说明判定依据
- 若怀疑原文为 AI 直接生成：先运行 `scripts/ai_trace_scan.py` 做机器快筛（读取文稿文本，输出 Markdown 残留、AI 高频词、模板句命中），再按 `references/03-ai-trace-checklist.md` 人工定性——**单信号不定罪，多信号 + 整体判断才定性**，避免误伤
- 涉及数据、引用、人名、事件、政策表述的可疑内容，单独记录，进入 Step 5

### Step 3.5：口径与分寸审查

- 针对单位正式材料（总结、汇报、宣传稿、新闻稿等），加载 `references/09-tone-and-caliber-review.md`，按四类风险初筛：
  1. 表述过满、过绝对的词句（"全面完成""显著成效""创新做法"等升级表述）
  2. 可能超出本单位层级或职责边界的判断
  3. 需要核对上级统一口径的提法
  4. 成绩、问题、措施之间分寸不稳的段落
- 每条风险**只列原句 + 风险点 + 降档方向，不代下最终结论**——是否修改由调用者对照政策、上级口径与单位实际定夺
- 文本带 AI 痕迹时（联动通病五），重点核查"语气抬升"类表述（AI 惯于把"有所改善"写成"明显提升"）
- 需核对统一口径的提法，并入 Step 5 待核查清单；报告中等同严重度、排在文采问题之前

### Step 4：证据与分级

- 每条问题统一标注四项：**原文引用 / 通病类别 / 严重度 / 位置**
- 严重度分级标准：
  - **严重**：影响文章成立或传播安全——文种用错、事实失实、逻辑主线断裂、导向性表述错误、口径风险（表述过满/层级越界/口径待核）
  - **中等**：明显影响阅读体验与说服力——段落割裂、论据脱节、用词明显不当、AI 痕迹明显
  - **轻微**：细节瑕疵——个别标点、个别赘词、格式不统一
- 分级结果直接构成报告的问题清单主体

### Step 5：事实核查（交互分支）

- 将 Step 3 记录的可疑内容整理成**待核查清单**，按 `references/07-fact-check.md` 的规则组织（逐条：原文引用 + 疑点 + 建议核查渠道 + 优先级）
- **停下来询问调用者**是否执行内容核查。不默认执行，原因：核查耗时且并非每次审稿都需要
- 调用者确认核查：
  - 使用全网检索对每条进行核查，优先官方渠道与一手来源，交叉验证
  - 每条给出四态结论之一：**属实 / 失实 / 存疑 / 无法核实**，并附来源
  - 核查结果写入报告"事实核查结果"板块；发现失实内容时，修订稿中必须替换或删除
- 调用者选择不核查：
  - 清单原样保留在报告中，状态标注**待核查**
  - 给作者附上自查建议（去哪查、怎么查）

### Step 6：修改建议与改写示范

- 对 Step 4 清单中的每条问题给出三件套：**病因**（为什么会犯）/ **改法**（怎么改）/ **示范**（改后示例句）
- 示范句必须贴合原文语境与文种风格，参考 `references/06-rewrite-examples.md` 与 `references/05-logic-tools.md`
- 逻辑类问题（通病二）优先给出重构建议，如调整段落顺序、补过渡句、删掉与主线无关的内容

### Step 7：输出审稿报告

- 按 `assets/review-report-template.md` 模板组织报告，包含五个板块：
  1. 总评（整体判断 + 单位规范符合性 + 结论：可直接发布 / 修改后可用 / 需重写）
  2. 分级问题清单（严重 / 中等 / 轻微）
  3. 事实核查结果（或待核查清单）
  4. 亮点与保留（做得好的地方要肯定，避免全盘否定打击写作积极性）
  5. 修订稿说明（改动对照摘要）
- 若已配置单位规范：总评中逐条核对单位要求，违反项必须列入问题清单并标"按单位要求判定"

### Step 8：产出全文修订稿

- 基于问题清单产出修订版全文，遵循以下规则：
  - 保留原文信息与个人风格，不无谓重写；可改可不改的不改
  - 失实内容必须替换或删除（见 Step 5）
  - 附**改动对照说明**：改动位置、原文与改文、改动原因，便于调用者复查
- 修订稿与报告一并交付

## 输出规范

- 审稿报告使用 Markdown 呈现，问题清单使用表格（列：序号 / 位置 / 原文 / 问题 / 病因 / 建议 / 示范）
- 修改建议必须具体可执行，禁止"语言不够优美""建议优化"类空话
- 示范句必须与原文语境、文种风格一致；同一问题可给 1-2 个示范
- 全程保持建设性语气：指出问题的同时肯定亮点

## 配置单位规范（可选，推荐）

用户可将所在单位的稿件硬性要求配置为审稿**最高准则**（用于：单位特有的格式规范、领导排序惯例、必写/禁写要素、禁用词等）。两种配置方式：

1. **让 AI 配置**：用户把单位的制度文件、格式要求或审稿要点粘贴在对话中（或上传文件），并要求"配置到 copy-review 的单位规范"时——通读材料，提炼出**可判定的硬性要求**（剔除空话），按 `config/org-rules.md` 的六个维度归类整理后写入；若文件已有内容，保留原条目、合并去重，冲突处以用户最新提供的为准。完成后告知用户已写入哪些条目。
2. **手动配置**：用户直接编辑 `config/org-rules.md`。编写指南见 `config/README.md`。

配置要求：**每条表述必须具体、可判定**（如"导语不超过 80 字"），禁写"注意格式"类无法核对的条目。配置后审稿自动生效（Step 1 加载），无需其他操作。
